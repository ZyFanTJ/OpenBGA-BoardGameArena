# 静态资源与首页性能

## React 大厅（2026-10-24）

大厅首页和房间大厅改用 React 19、Radix UI 和 Lucide。入口仍由原平台壳层管理，游戏牌桌、房间协议与持久化规则保持原有边界。`apps/web/lobby/app.jsx` 提供页面组件，`lobby/state.js` 管理公开目录状态，`lobby-surface.js` 负责按需加载、外部搜索同步与页面卸载。

- 搜索、分类和分页由状态驱动，目录只渲染当前页。游戏卡片、横幅、牌桌推荐和好友侧栏通过稳定键和 memo 复用；好友心跳不再通过 `innerHTML` 重建整块侧栏。
- 目录列数来自 ResizeObserver，并合并到动画帧。筛选与翻页不再同步读取网格样式后逐个修改全部卡片的 hidden 属性。
- 房间刷新保留筛选条件及现有卡片，后台更新不销毁输入框。离开页面会卸载 React root、清理订阅及观察器；晚到的请求和模块不能重新显示旧页面。
- 创建与加入房间继续复用已验证的原生 dialog 表单，置于 React 根节点之外。桌面加入表单与手机弹窗分别拥有独立 DOM，避免移动 React 管理的节点。
- 大厅包仅在进入大厅或房间目录时加载。构建使用本地安装并锁定的依赖，不请求第三方 CDN。构建产物位于忽略的 `apps/web/dist/`；`npm start`、`npm run dev` 和 `npm test` 先构建，Docker verified 阶段执行 npm ci 和同一构建。

当前大厅和目录共享的生产包约 315 KiB，单独使用 Node Brotli 压缩约 87 KiB。这里是包体积，不代表公网加载或交互耗时；框架迁移并不保证网络请求、图片解码或服务端操作自动变快。

验证覆盖分类的方向键操作、桌面及手机搜索、翻页、好友资料、游客加入公开房间、创建房间、CABO AI 开局与返回大厅，以及多种屏幕宽度。状态与生命周期回归测试位于 `tests/lobby-react.test.js`。

原素材保留，版式和游戏动画保持不变。早期 WebP 使用无损编码，独立封面和展示牌仅裁切原图；2026-10-24 新增适合实际展示尺寸的有损 WebP 派生资源，见下文。

## 首页

- 游戏渲染器通过 `games/lazy.js` 在真正展示牌桌时加载。大厅只读取游戏元数据和轻量封面，等待房间也不会加载三个游戏的交互模块。离开页面后，未完成的加载不能重新覆盖当前页面。
- 游戏卡片初始隐藏，目录测量列宽后只显示当前页，避免首次布局就下载所有隐藏封面。翻页、搜索和分类会加载对应原图裁片。
- 主横幅在进入大厅时标记高优先级预加载；其他子页面不会额外下载横幅。七大奇迹封面使用原生图片懒加载。

## HTTP

`apps/server/static.js` 负责公共文件的静态响应。HTML、JavaScript、CSS、SVG 使用 Brotli 或 gzip，编码结果按文件的修改信息缓存在进程内；更新文件会重新计算内容和 ETag。

带 `-v数字` 的图片使用一年 immutable 缓存。代码、样式和 HTML 使用 `max-age=0, must-revalidate`，通过内容 ETag 返回 304，更新后仍及时获取新版本。压缩响应包含 `Vary: Accept-Encoding`。HEAD、文件不存在和原始 PNG 兼容路由保留。

API、会话、玩家资料、房间快照与 SSE 保持 `no-store`，不进入静态文件缓存。

2026-10-20，本机浏览器桌面首页，首屏显示五张游戏卡片。这里比较传输体积，不将本机耗时当作公网速度。

| 项目 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 首页图片正文 | 10,400,668 B | 4,248,388 B（减少 59.2%） |
| 未进入游戏时的完整游戏渲染器 | 三款一并加载 | 不加载 |

浏览器验证覆盖首页画面对照、封面翻页、搜索和三款桌游的创建、AI 开局及交互；测试包含压缩协商、ETag、HEAD、文件更新失效、玩家数据不缓存和异步渲染器生命周期。

## 房间操作、持久化与同步（2026-10-22）

生产存储改为内置 SQLite，保持原 `transaction(update)` 服务接口。`transaction-draft.js` 仅复制实际访问的记录，SQLite 仅提交真正变化的行。房间、战报与钱包仍能在同一个事务中提交；失败不更新内存，空事务不落盘。WAL + FULL 保留先持久化、后响应/广播的顺序。写入仍是同步的、但工作量限于受影响记录；当前部署仍为单应用进程。

旧 JSON 只在数据库首次初始化时导入，原文件和原加密密钥保留。生产默认数据库为 `DATA_FILE + '.sqlite'`，支持 `DATABASE_FILE`。所有现有游戏内部状态形状和版本保持不变。

本机合成基准使用相同历史记录、相同单房间 revision 更新，各运行 11 次，包含提交时间，比较中位数。FULL 提交受本机磁盘同步开销影响，这些数字不代表公网操作延迟或线上吞吐。

| 合成历史体积 | 旧 JSON | SQLite 按记录事务 |
| --- | ---: | ---: |
| 0.86 MiB | 9.259 ms | 12.100 ms |
| 8.66 MiB | 89.712 ms | 36.304 ms |
| 43.37 MiB | 801.872 ms | 73.124 ms |

小存档的本次基准没有更快；大存档收益来自去除整库复制、序列化和重写。另有测试断言更新房间不复制/持久化无关战绩，不能只用耗时阈值判断正确性。

传输与交互调整：

- 已认证写请求按玩家 ID 限流；登录/注册按来源与账号分别限制。只有显式配置可信代理层数时读取转发地址，生产 Caddy 为唯一入口。
- API 的连接和响应正文合计最多等待 12 秒；超时写请求核对牌桌、不自动重放。房间写操作独立排他，菜单、聊天、查看和导航保持可用，旧响应不能把玩家带回离开的房间。
- 独立提交由游戏声明 `submissionKey`，在同一事务内检查当前 revision、matchId、窗口、本人资格和合法动作。顺序行动保持严格版本匹配。
- `events?protocol=2` 把聊天和流式展示拆成小消息。聊天不重算游戏视图；DND 流式更新只投影 `narrationStream`。旧客户端兼容完整快照。受阻连接不堆积事件，恢复时发送最新私密快照，超过 15 秒关闭重连。

浏览器在隔离 SQLite 数据上验证了七大奇迹开局/选牌/回合推进、双标签页实时聊天、聊天不关闭选牌弹窗、刷新恢复；人为延迟 14 秒的 CABO 请求期间仍可打开/关闭菜单和发送聊天，12 秒超时后保留已提交的准备状态；DND 通过本地合成提供器验证片段到完整叙述、日志工具可用和额外提供器字段未显示。没有调用外部模型服务，测试数据和截图均位于忽略的 `work/`。

## 按页加载与查询成本（2026-10-24）

### 页面与资源

- `hub/data.js` 明确每个页面的数据依赖：商城只请求商店，战绩只请求历史；好友和资料页保留其需要的外观目录，不再等待无关历史数据。异步结果在导航代次和玩家身份仍一致时才写入页面状态。
- `/games` 与 `/me` 并行启动；站点名称和公告后台加载，不阻塞目标页面。API 只合并同时在途的相同 GET，完成后即清除；任何写请求都会使在途读请求映射失效，身份、钱包、房间和快照不做持久缓存。
- 管理中心和论坛模块首次打开时加载。`lazy-surface.js` 负责离开页面后的失效处理及失败重试；`styles-loader.js` 合并样式请求，并等样式加载成功后显示对应界面。
- CABO 的移动布局/手卡/呼叫效果、七大奇迹的牌图和交互扩展、DND 的沉浸/游玩/插画样式，以及忍者之夜牌桌样式随游戏加载。用于大厅封面与创建表单的公共样式仍保留。样式加载后复用，不在切页时反复移除和下载。
- `scripts/prepare-display-assets.py` 从原图生成展示资源，使用新的版本文件名，避免破坏旧 immutable 缓存。卡坦岛棋盘保持 1536×1024 和原图集坐标；列表使用独立的 768×512 预览。

| 资源 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 大厅横幅 | 1,350,276 B | 132,722 B |
| 大厅侧栏插图 | 1,641,902 B | 20,394 B |
| 卡坦岛列表预览 | 3,889,836 B | 160,416 B |
| 卡坦岛棋盘贴图 | 3,889,836 B | 647,134 B |
| 静态首屏 JS 依赖 | 38 文件 / 236,150 B | 36 文件 / 200,903 B |
| 静态首屏 CSS 依赖 | 35 文件 / 477,801 B | 20 文件 / 265,437 B |

依赖数据来自源码静态导入图，不是浏览器实际请求数。按每文件 Brotli quality 5 计算，JS + CSS 从 198,073 B 降到 134,828 B；没有把图片或 HTTP 头算入该数值。显示图片按展示尺寸进行视觉检查；有损派生图不再宣称逐像素一致。

### 存储与计算

- `record-index.js` 只管理派生索引，索引键由房间、战绩、社交、资料、钱包各服务声明，平台没有导入特定游戏规则。SQLite 在成功持久化后增量维护索引；回滚不更新索引。查询仍从当前已提交数据取值，重启后首次查询建立索引。其他存储适配器保留扫描回退。
- `storage-layout.js` 将 `forum.topics` 映射为独立 SQLite 记录；领域对象仍是原来的 `forum: {nextNumber, topics}`。修改单个话题仅复制和提交该话题；计数器和话题仍在同一个事务提交。
- **迁移**：启动时识别旧的论坛单记录，在同一 SQLite 事务中拆分话题并更新元数据。失败时旧数据保留；再次启动可以重试。没有改变任何游戏持久状态的形状或版本。升级前应按部署流程备份数据库；旧版程序不认识 `forumTopics` 物理记录，回退旧程序需要恢复升级前备份，不能直接打开升级后的数据库。
- 机器人仍在提交顺序中观察自己的玩家视图，但决策延迟到计时器执行时，避免 HTTP 响应等待所有机器人决策。执行前核对 revision，找到可行动者后停止本轮后续决策。计算仍在主线程，**这不是工作线程隔离**；若负载测量显示长决策，应进一步做独立计算池。
- JSON API 增加 `Server-Timing: app;dur=...`，包含从请求处理开始到正文序列化完成的服务端耗时；不包括客户端网络传输或浏览器渲染，不输出令牌、参数或快照。

### 复测方法与边界

运行 `node scripts/benchmark-performance.mjs` 可重复测量静态依赖、合成历史/论坛成本及隔离内存 SQLite 上的本机接口。每项先预热，再取 11 次样本；首次建立索引不计入热查询。数据生成与记录替换也不计入计时。

| 合成场景，中位数 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 50,000 条战绩，其中 10% 属于当前玩家 | 15.51 ms | 0.97 ms |
| 10,000 个话题，约 10.75 MB，修改单条 revision 的草稿复制与差异计算 | 76.44 ms | 0.01 ms |

论坛数字不含磁盘提交；空数据 HTTP 中位数仍约 0.5–1.4 ms，不能据此推断公网延迟改善。测试覆盖查询索引增删、整集合替换、持久化失败回滚、旧论坛迁移/重启、无关话题不访问、延迟加载导航失效、GET 合并与写操作失效。完整回归运行 `npm test`。

尚未引入代码内容哈希构建、CDN、跨进程缓存或多应用实例。代码继续 ETag 重新验证；需要用真实网络和并发指标决定后续部署优化，不应给玩家视图加共享缓存，也不能直接启动多个持有独立内存状态的应用实例。

本次最终完整回归为 386 项通过。浏览器使用隔离的 `work/` 数据验证了商城、好友、战绩、资料、论坛发帖/回复/刷新、CABO 开局、七大奇迹选牌提交、忍者之夜轮抽、卡坦岛压缩棋盘，以及本地引导跑团的角色创建与刷新恢复。未调用外部模型服务，未部署到生产环境。
